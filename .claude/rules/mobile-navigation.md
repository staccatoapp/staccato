# Mobile Navigation & Detail Screens

The mobile app (`apps/mobile`, Expo + expo-router, SDK 56 — read the v56 docs per `apps/mobile/AGENTS.md`). The root layout `src/app/_layout.tsx` is a `<Stack>` with two auth-guarded branches via `Stack.Protected`: `(auth)` when signed out, `(protected)` when signed in. The `(protected)` group's layout renders `AppTabs` (`components/app-tabs.tsx`) — `NativeTabs` from `expo-router/unstable-native-tabs`, one tab per child route (`(home)`, `explore`, `library`, `settings`).

This rule covers navigation, routing, and detail-screen mechanics. The shared, reusable UI components these screens compose — `TrackRow`, `MediaTile`, `AlbumArt`/`StaccatoImage`, the bottom-sheet tiers, toasts, and the `components/ui/` design-system primitives — live in [[mobile-ui-components]]; cross-screen client state (sheet store, downloads store) in [[mobile-state]].

## Detail screens push within a tab's own Stack (keep the tab bar visible)

A detail screen (album and playlist today; artist is a pending TODO that must follow this) must **push within its tab so the native tab bar stays visible** — it must NOT be a root-Stack sibling (that covers the tab bar). The pattern is "Stack inside native tabs": a tab that hosts detail screens is a **folder** with its own `_layout.tsx` (`<Stack>`), an `index.tsx` (the tab screen), and the detail routes nested under it. So `library.tsx`/`explore.tsx`/`settings.tsx` became `library/index.tsx`+`library/_layout.tsx`, `explore/index.tsx`+`explore/_layout.tsx`, and `settings/index.tsx`+`settings/_layout.tsx`; library/explore each nest `album/[albumKey].tsx` and `playlist/[playlistKey].tsx`, and settings nests `account`, `listenbrainz`, `about`, and an `admin/` subtree (`library`, `integrations`, `lidarr`, `maintenance`, `users/{index,new,[userId]}`). The home tab is a **group** folder `(home)/` (`(home)/index.tsx`+`(home)/_layout.tsx` nesting `album/[albumKey].tsx`, `playlist/[playlistKey].tsx`, and `rec-playlist/[playlistKey].tsx`) so its recently-played grid (album/in-library-playlist) and its recommended carousels/hero (rec-playlist) can push detail within the Home tab. It MUST be a group (parens), not a plain `home/` folder: a group adds no URL segment, so `(home)/index.tsx` owns `/` — and the app needs a route matching the cold-launch URL `/`, or React Navigation's async first pass builds no initial state and the app hangs on a **black splash with no error** (per the `expo:building-native-ui` "always have a route that matches `/`, it may be inside a group" rule). A plain `home/` folder maps its index to `/home`, leaving `/` unmatched → black screen on launch; a folder literally named `index/` instead collapses to the group index and breaks nested navigation ("unmatched route" on push). The home trigger is `name="(home)"`; `(protected)/_layout.tsx` sets `unstable_settings = { initialRouteName: "(home)" }`. **Invariant: the home/first tab must be a transparent group so its `index.tsx` owns `/`.** Each per-tab `_layout` sets `unstable_settings = { initialRouteName: "index" }`. A folder-index route is referenced with the explicit `/index` href (e.g. `router.push("/(protected)/settings/admin/users/index")`); leaf routes omit it.

## Settings surface (segmented Personal/Admin, mostly unbacked)

The settings tab (`settings/index.tsx`) is an iOS grouped-list built from `components/settings/` primitives (`SettingsGroup`, `SettingsRow`, `SettingsSwitch`, `Segmented`, `CheckList`, `AdminBanner`, decorative `tiles.ts`). Detail screens wrap their body in `SettingsDetailScreen` (a custom top nav bar with a `router.back()` chevron + centered title over a `useContentBottomInset({ tabBarAutoInset: false })` scroll view; the native Stack header stays hidden per convention). The **Admin** segmented control renders only when `useCurrentUser().isAdmin`; derive the active segment (don't sync it in an effect). Most of the design isn't backed by the server, so unbacked features (display name/email, appearance, networking, downloads, localization, remove/role-change user, uptime/DB size/restart) render as **greyed `SettingsRow dim`** placeholders, never as working controls. Backed pieces: account (username/role/instance + sign-out), ListenBrainz token, server version (`/api/health`), library scan, Lidarr config, list/add users. View-model helpers live in `lib/settings-view.ts` (pure, unit-tested); the data hooks (`use-current-user`, `use-server-health`, `use-user-settings`, `use-scan`, `use-lidarr`, `use-admin-users`) are thin wrappers over `useAuthedQuery`/`useAuthedMutation`. PATCH endpoints use `ApiClient.patch` (added alongside get/post/put/delete).

The album screen is shared across the tab stacks via one `components/album/album-screen.tsx`; the per-tab route files are thin wrappers passing their own `basePath` (`/(protected)/library/album/[albumKey]`, `/(protected)/explore/album/[albumKey]`, or `/(protected)/(home)/album/[albumKey]`) so a "More by artist" tap pushes the sibling onto the _same_ tab stack. The playlist screen (`components/playlist/playlist-screen.tsx`) is shared the same way, but its wrappers pass a `mode` rather than a basePath, since it has no sibling-push rail: `"recommended"` from explore's `playlist/` and home's `rec-playlist/`, `"inLibrary"` from library's and home's `playlist/`. Navigate to a detail from a tab's content using that tab's pathname.

Typed routes are on (`app.json` → `experiments.typedRoutes`). Navigate to a **dynamic** route with the object form — `router.push({ pathname: "/(protected)/library/album/[albumKey]", params: { albumKey } })`. The string-interpolation form (`/album/${id}`) is not generated for dynamic segments and fails `tsc`. After adding/moving routes, route types regenerate on `expo export` (the build) or a running dev server.

Wrap a screen body in `<Screen>` (`components/ui/screen.tsx`) for the `stacScreenIn` entrance animation; the Stacks use `animation: "none"` because screens own their own entrance.

## Scroll content must clear the mini player and tab bar

The mini player (`components/player-overlay.tsx`) is a root-level absolute overlay floating above the native tab bar, so nothing in a screen's tree knows it's there — every vertical scroll surface must reserve bottom space for it explicitly, or its last items get clipped. `lib/player-layout.ts` owns the geometry (`TAB_BAR_CONTENT_HEIGHT`, `MINI_PLAYER_INSET/HEIGHT/CLEARANCE`, consumed by the overlay itself) and the `useContentBottomInset({ tabBarAutoInset })` hook that returns the `contentContainerStyle.paddingBottom` a scroll view needs. Space is reserved unconditionally (assume the mini player is always present). Pass `tabBarAutoInset: true` for tab-root scroll views that set `contentInsetAdjustmentBehavior="automatic"` — NativeTabs already insets the tab bar + bottom safe area (SDK 55+), so only the mini player is added. Pass `false` for nested detail screens (album/playlist) that manage their own top inset via the hero and set no `contentInsetAdjustmentBehavior`; the hook then adds the tab bar + bottom inset too. Never set `contentInsetAdjustmentBehavior="automatic"` on the detail screens — it double-counts the hero's manual `insets.top`.

## Collapsing hero (shared by album + playlist; artist must follow)

`components/detail-hero-layout.tsx` is the shared scaffold for detail screens: it owns the gradient, the scroll view, the persistent back + **More** buttons, the collapsed title, and all collapse animation (reanimated v4 worklets). `AlbumHero`/`PlaylistHero` are now plain layout (no animation, no top bar) passed as the `hero` prop — the layout wraps them in the fading `Animated.View`, so heroes must reserve top space (`paddingTop: insets.top + 52`) to clear the floating buttons. All motion is driven off the **measured** hero height (`onLayout`), never fixed pixel thresholds, so it scales with content. The pure geometry lives in `lib/hero-collapse.ts` (`heroCollapseDistance` + the content/title fade input-range helpers), unit-tested; keep new collapse math there. Mechanics: the backdrop gradient translates up 1:1 with scroll then clamps (its bottom band becomes the bar); the whole hero fades out over the first ~60% of the collapse; a separate sticky bar + the collapsed title fade in over the last stretch. Two gradient layers exist on purpose — the backdrop sits _behind_ the scroll view (hero paints over it) and the sticky bar renders _in front_ (so rows scroll under it); both reuse one `GradientStack` so the hand-off is seamless. The back/More buttons and title paint above the bar. Play is deliberately absent from the collapsed bar.

## Album detail conventions

`:albumKey` is either a local cuid2 album id (owned albums, opened from the library grid / in-library search) or a MusicBrainz release-group MBID (explore-search albums). `GET /api/albums/:albumKey` resolves either to a `source: "local" | "external"` `UnifiedAlbumDetail`. Fetch via `hooks/use-album-detail.ts`; the "More by artist" rail fetches the artist's discography via `hooks/use-artist-detail.ts` (local artistId or MB artistMbid).

Availability is **album-level**, not per-track — the API gives no per-track ownership. `lib/album-view-model.ts` derives it: local with `pendingTrackCount === 0` → in-library; local with pending > 0 → partial (`N of M`); external → found-on-MusicBrainz. Pure view-model helpers (availability, totals, eyebrow, `albumTrackRows`, `playableTrackIds`) live there and are unit-tested; keep new album logic pure and tested there rather than in components.

Lidarr requests are album-level (release-group MBID). `AddAlbumSheet` (`components/explore/add-album-sheet.tsx`) handles the request; `subjectFrom*` helpers in the same file build a `LidarrSubject` from track/release/album payloads. The sheet is opened via `useLidarrSheet()` from the global sheet store (`stores/sheet-store.ts`), rendered once by `GlobalSheetHost` at root so it floats above all overlays. A subject is only buildable for **external** albums — local album detail omits `artistMbid` — so the request affordance is external-only. A **local** album hero instead shows an offline `DownloadButton` (in the Heart's old slot); the per-collection download feature is its own subsystem ([[mobile-storage]]).

## Playlist detail conventions

Two data sources feed one screen, chosen by `mode`. **Recommended** (explore): selected by id out of the cached `useRecommendedPlaylists` list — the list embeds every playlist's full tracklist with live `inLibrary`/`localTrackId`, so no extra fetch (`hooks/use-recommended-playlist.ts`). **In-library** (library): `GET /api/playlists/:id` via `hooks/use-playlist-detail.ts`; every track is owned. Pure mapping + tests live in `lib/playlist-view-model.ts` (`playlistViewFrom{Recommended,Library}` → one `PlaylistView`); keep new playlist logic there. The server's playlist-detail/list/update responses carry a `coverArtUrls` mosaic (up to 4) and per-track `recordingMbid`; the hero renders the mosaic via `AlbumArt artUrls` (recommended uses the single `coverArtUrl`).

Per-track Lidarr requests (recommended, not-in-library rows) reuse `AddAlbumSheet` + `subjectFromPlaylistTrack`. The recommended hero's "Add all to library" button opens `AddAllSheet` (`components/playlist/add-all-sheet.tsx`) — a visual stub (no bulk endpoint exists). It opens via `useAddAllSheet()` from the global sheet store (`stores/sheet-store.ts`), rendered by `GlobalSheetHost` at root so it stays above all overlays; the screen calls `addAllSheet.open(view)` directly. In-library playlists end with a `PlaylistSuggestions` block (`GET /api/playlists/:id/suggestions`): three picks, +/× to request-or-dismiss, refresh to re-roll; slot rotation state is kept in component state (no refs during render). The in-library hero also carries an offline `DownloadButton` (see [[mobile-storage]]); the screen builds its descriptor with `playlistDownloadable`.

Mobile tests use **jest** (`jest-expo`, `@testing-library/react-native`), not Vitest. `expo-router` and `react-native-safe-area-context` are mocked (the latter globally in `jest-setup.js`).
