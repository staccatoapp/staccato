# Mobile Persistent Storage (blob store + artwork cache)

The mobile app (`apps/mobile`, Expo SDK 56 — read the v56 docs per `apps/mobile/AGENTS.md`) keeps a generic on-disk cache under `src/lib/storage/`. It exists because lock screens fetch artwork URLs themselves and cannot attach the `Authorization: Bearer` header that Staccato's server-relative cover URLs (`/metadata/covers/<mbid>.jpg`, served behind `requireAuth`) require, and the server exposes no unauthenticated/query-token cover endpoint. So the app must download cover bytes itself (with the header) to a local file and hand the lock screen a `file://` path.

## The blob-store primitive (`blob-store.ts`)

`createBlobStore(config, fs?)` returns `{ ensure(key, url, opts?), uri(key), remove(key), clear() }`. `config` is `{ name, baseDir: "cache" | "document", indexKey, maxBytes? }`. `baseDir` chooses `Paths.cache` (OS-evictable; artwork) or `Paths.document` (durable; offline downloads). `ensure` downloads `url` (with optional `opts.headers`) to a deterministic file and returns its `file://` uri; concurrent calls for the same key share one in-flight promise (dedup map). A cache hit that finds the indexed file missing on disk (OS reclaimed `Paths.cache`) re-downloads. `uri(key)` returns the already-cached `file://` uri (or null) **without** downloading — the read path for pinned downloads. Filenames are an FNV-1a hex hash of the key plus a per-`ensure` extension (`opts.extension`, default `jpg`; downloads pass the source file extension so the player can decode a local file that carries no Content-Type). When `maxBytes` is set, after each add it evicts least-recently-used entries (by `lastAccessedAt`) until under the cap, never evicting below one entry. A hit refreshes `lastAccessedAt` so hot entries survive.

The index (`key → { filename, bytes, lastAccessedAt }`) is a single JSON value in async-storage under `config.indexKey` — kilobytes of metadata only; image bytes never go in async-storage. It is lazily loaded once and persisted after every mutation. Corrupt/missing index parses to empty.

Filesystem access goes through a small injectable `BlobFs` adapter (`ensureDir`, `uriFor`, `exists`, `download`, `remove`), defaulting to an expo-file-system implementation (`new File(Paths.cache, name)`, `File.downloadFileAsync(url, dest, { headers })`, `file.exists`, `file.size`, `file.delete()`). Tests inject a fake `BlobFs` so the index/dedup/eviction logic is exercised without the native module.

## The artwork cache policy (`artwork-cache.ts`)

A single module-level `createBlobStore({ name: "artwork", baseDir: "cache", indexKey: "staccato.artworkCache.index", maxBytes: 50MB })`. `ensureArtworkFile(coverArtUrl, session)` runs the URL through `resolveImageSource` (`../image-source.ts`) — which absolutises server-relative paths and attaches the Bearer header, passes absolute façade URLs through verbatim with NO header (never leak the token to a third party), and returns null for nulls/sentinels — then `store.ensure`s the resolved uri (keyed by that uri, so every track on an album shares one file). Returns null on no cover / no session / download failure (logged via `console.warn`), so callers just render no art.

## Playback-provider wiring

`playback-provider.tsx`'s track-change effect fires `ensureArtworkFile(track.coverArtUrl, authSession)` and, when it resolves, stores the `file://` uri in a `lockArtworkUri` state (reset to undefined at the top of each track change so a previous cover can't leak). A per-effect `cancelled` flag (set in the effect cleanup) suppresses a stale previous-track download from clobbering the state; it never blocks the new track's own update. A separate readiness-gated effect actually publishes the lock screen: only once `status.isLoaded && status.duration > 0` does it call `player.setActiveForLockScreen(true, { title, artist, albumTitle, artworkUrl: lockArtworkUri }, { isLiveStream: false })`, re-running when `lockArtworkUri` resolves to attach the cover. The duration gate plus `isLiveStream:false` is load-bearing: publishing right after `player.replace()` while duration is still 0 makes iOS render the Now Playing widget as a live stream ("LIVE", no scrubber). expo-audio still exposes no lock-screen next/prev remote commands (those are coming upstream in expo/expo#46020), so only play/pause/seek work from the lock screen today. This all runs while the device is locked because background audio (`shouldPlayInBackground: true`) keeps the JS engine alive — the same context the 5s position-sync interval and `didJustFinish` auto-advance use — and the queue advance flips `currentTrackIndex` via an optimistic update with no network dependency. Before streaming, the track-change effect reads `useDownloadsStore.getState().trackUris[track.id]` imperatively (no subscription) and, when a downloaded file exists, `player.replace`s the `file://` uri with **no** headers; otherwise it streams with the Bearer header.

## Offline downloads (`download-cache.ts` + `stores/downloads-store.ts`)

Phase 1 of offline play. `download-cache.ts` is the durable policy module mirroring `artwork-cache.ts`: one `createBlobStore({ name: "downloads", baseDir: "document", indexKey: "staccato.downloads.index" })` (no `maxBytes`; pinned). `ensureTrackDownloaded(trackId, fileExtension, session)` ensures the `${serverUrl}/api/tracks/${trackId}/stream` audio under key `audio:<trackId>` with the Bearer header + extension (throws on failure so the caller marks the track); `getDownloadedTrackUri(trackId)` is the no-download `store.uri` lookup; `ensureDownloadedArt(coverArtUrl, session)` pins the cover (best-effort, swallows). The download extension is the **source file's container extension**, not the codec label: the server derives `fileExtension` via `path.extname(filePath)` (`db/queries/fileExtensionFromPath`) and exposes it on `PlaylistTrackSchema` + `UnifiedAlbumLocalTrackSchema`. Do NOT use `tracks.fileFormat` (a codec label like `vorbis`/`alac`/`aac`, kept server-internal for the stream MIME map + graphWalk) as a filename extension — iOS sniffs the extension off the headerless local file and can't decode `track.alac`.

`downloads-store.ts` is a **zustand** store (see [[mobile-state]] — plain shared state, not a Provider) holding per-collection `{ state, completed, total }` and a `trackUris: Record<trackId, fileUri>` map. `download(collection, session)` pulls each owned track sequentially (tracking a `downloaded` set of trackIds to drive the determinate ring; a `partial` retry seeds the set from already-present `trackUris` so the ring resumes instead of resetting to 0/total), pins the collection covers **and** each track's own cover (best-effort), then persists a manifest entry to async-storage (`staccato.downloads.collections`: id/kind/name/trackIds/snapshot/downloadedAt — the snapshot is the raw server detail, kept for future offline rendering). Manifest writes are serialised through a module-level promise chain, since `download()` is fire-and-forgot and two concurrent collection downloads would otherwise interleave their read-modify-write and clobber an entry. `hydrate()` (called once from `app/_layout.tsx`) rebuilds `trackUris` + status from that manifest on launch. The collection descriptor is built purely by `playlistDownloadable`/`albumDownloadable` (view-models) and surfaced by the shared `DownloadButton` (`components/downloads/`) on the in-library playlist hero and the local album hero (replacing the Heart). Only owned content is downloadable. Removing downloads, offline detail rendering, and zero-network queue construction are deferred to Phase 2.

`useCachedImageSource` remains deferred — its value is offline art rendering off the durable store (resolving durable-store-first → transient artwork cache → `resolveImageSource`), wired into now-playing + mini-player. Do NOT make `resolveImageSource` itself cache-aware: it is sync and called inline in render by many components, so going async would ripple a loading state everywhere.

## Native build gotcha (expo-file-system prebuilt ABI)

`apps/mobile/package.json` sets `expo.autolinking.ios.buildFromSource: ["expo-file-system"]` (and the same under `android`). The platform-nested `ios`/`android` placement is required — a top-level `buildFromSource` is not the documented form (autolinking reads `autolinking.ios` for the Apple platform). This is load-bearing, not optional. EAS enables precompiled Expo modules by default (`EXPO_USE_PRECOMPILED_MODULES=1` + prebuilt React Native), and `expo-file-system@56.0.8` ships a prebuilt `ExpoFileSystem.xcframework` compiled against an older `expo-modules-core` whose `Record` API was `from(dictionary:appContext:)`. The project resolves `expo-modules-core@56.0.14` (pulled up by newer modules like `expo-router`), which renamed that to `convert(from:)`. Linking the stale prebuilt against core 56.0.14 makes the app abort at launch with a dyld "Symbol not found: ExpoModulesCore.Record.from(dictionary:appContext:)" before any JS runs — and `eas build --clear-cache` does NOT fix it, because prebuilt binaries are not recompiled. `buildFromSource` forces the module to compile from source against the real core. If the offline-downloads feature adds more native modules, watch for the same prebuilt-vs-core ABI skew.

## Tests

Mobile uses jest (`jest-expo`), not Vitest. `expo-file-system` and async-storage are mocked globally in `jest-setup.js`. Storage logic is tested with an injected fake `BlobFs`; `artwork-cache` tests mock `./blob-store` and capture the store instance the module built at import; the provider test mocks `@/lib/storage/artwork-cache`.
